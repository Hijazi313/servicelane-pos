## Approval record

On 2026-10-22 the user approved preparation-only data (KT-D02), and approved the development boundary comprising Kitchen-owned queued→preparing→ready, existing staff/admin access, immutable dispatched tickets and no amendment/cancellation API (KT-D03–04). This does not authorize implementation or restaurant operation. Free-text instructions may contain personal data; this approval permits preparation instructions, not a new customer-data policy.

KT-D01 was subsequently resolved: the user selected “Approve explicit dispatch for this increment” in response to the question explicitly allowing preparation before payment and retaining branch-configurable flows as a future product direction. Thus capture alone sends nothing; current authorized staff/admin explicitly release a captured order without a payment prerequisite in this development slice. No automatic dispatch, settings API, payment gate, delegated branch-admin role or implementation is authorized. The alternatives above remain rationale, not outstanding questions. No full technical specification acceptance is inferred beyond these business choices.

## Dispatch configuration recommendation and reference evidence

Reviewed official [Toast UI settings](https://doc.toasttab.com/doc/platformguide/adminUiOptionsReference.html) on 2026-10-22: Send can release preparation without payment, Hold saves without sending, and a payment-first setting exists with documented takeout/delivery exceptions. Authorized setup users can apply settings to selected locations. [Toast online-ordering guidance](https://support.toasttab.com/en/article/Getting-Started-Online-Ordering) also documents manual approval and automatic kitchen release for that separate channel. These examples support multiple valid workflows; they establish neither a universal industry standard nor a requirement to copy Toast’s exceptions.

Future mechanism recommendation, not yet approved: ultimately use branch-scoped dispatch policy managed by the existing business administrator with current branch authorization. A dedicated/delegated branch-admin role does not exist and needs a separate permission decision. Implement only explicitly supported modes; keep automatic capture dispatch and payment-gated dispatch deferred for this smallest slice. Do not build a one-option settings API, generic rule engine, business-default/branch-override hierarchy or per-channel exceptions without a concrete approved requirement. The first real second mode justifies a revision-checked policy API, supported-mode validation, prospective-only changes, auditable actor/time and transactional policy enforcement; it must specify the treatment of already captured undispatched orders. No policy change may silently send an old backlog or withdraw existing tickets. Payment-first must rely on trusted Billing state, never a cashier assertion. Automatic capture dispatch needs explicit reconsideration of Orders transaction/retry behavior. These later objectives are not activated.
