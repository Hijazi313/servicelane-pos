## Technical design candidates and validation gates

The required invariant is atomic payment/attribution and an unambiguous close boundary. CS-01 uses Billing-to-Shifts calls in the existing Access transaction without nested authorization. Source and synthetic tests do not prove PostgreSQL contention or rollback; bounded database evidence remains necessary.

The proposed Billing compatibility matrix below covers before source activation, covering: historical successful retries with original matching semantics; new requests without a session; requests targeting a closed/replaced session; successful retries after close or a new open; and isolated test composition while Billing remains absent from AppModule. For each, specify request compatibility, admission/result, attribution effects and recovery. There are no confirmed external Billing clients in the inspected evidence; inventory actual callers before claiming compatibility. Apply the REST skill when designing these contracts.

Subject to the decisions above:

- Under candidates A/B, Shifts could own session lifecycle, float/count/variance, retry identities and minimal immutable cash-attribution entries. Candidate C places association with Billing instead. Billing remains authoritative for bills, payment amount and its successful settlement retry. Never copy complete bills, customers, tax configuration or order instructions into Shifts.
- Candidate A has Billing invoke a narrowly exported Shifts capability inside its existing `runAuthorized` transaction; candidates B and C offer different ownership and dependency directions. See the [comparison](#integration-evidence-and-candidate-approaches). CS-01 selects candidate A for the isolated source implementation. Each must ensure settlement and attribution commit or roll back together and close totals are consistent.
- Do not invoke nested authorization, create another connection, emit an asynchronous attribution event or perform external I/O inside the transaction. Reuse current Access serialization and add persistence uniqueness/integrity backstops. Design explicit close-versus-settlement ordering before implementation: a payment either commits into the open session before close and is included, or fails admission after close; it never lands outside the count.
- A successful original settlement retry returns its original bill under current authorization, even after its session closes or another opens. It must not create another entry or move cash to the new session. An uncommitted request targeting a closed/replaced session conflicts and requires deliberate refresh/reconfirmation. Specify how intended session identity participates in new request normalization without breaking historical successful retry matching.
- Open and close need scoped durable retry identities too: same key/content returns the committed result; changed content conflicts. Closed sessions cannot reopen or accept additional payments. A new key cannot amend a closed count. Unknown outcomes recover with the original key or authorized known-session readback, not a fresh payment key.
- Money uses decimal-safe integer minor-unit arithmetic and explicit capacity limits, never floating point. Opening/count amounts are nonnegative; variance may be negative. Session currency/scale is frozen from validated Business context. Reject a new payment whose monetary context differs; do not change old amounts when business settings change. Set bounds and aggregate-overflow behavior in CS-00, with atomic rejection rather than truncation.
- Use server-resolved business/branch, verified actor and UTC timestamps; Business timezone is for display, not date-window attribution. Do not accept client actor, trusted branch, expected-sales total or variance as authoritative input.
- Read scope: current session discovery for staff; known-session close/readback for authorized administrators. Closed-session search, pagination and end-of-day reports are unnecessary for this first proof. Define a safe no-open state, bounded selected response fields and recovery without retained browser state in the contracts.
- Retain successful retry and cash-history records; no deletion, count editing or reallocation capability in this slice. Correcting a mistaken close is an unresolved operational requirement before restaurant use, not permission to overwrite history. Do not invent a legal retention period. Follow [compliance guidance](../../../../../../../../docs/compliance/README.md); this proposal makes no new legal or fiscal compliance claim.

The implemented routes and payload schemas are linked in the [integration guide](frontend-integration.md); source delivery does not imply acceptance or runtime activation. Finalize them using the REST skill and actual shared HTTP wiring. Keep existing BillView/readback stable unless a separately reviewed consumer need justifies change; the intended-session admission change is explicit scope, not an incidental addition.

## Reference day for the first release

Confirmed product requirements, 2026-10-28: each cashier has a separate drawer; multiple cashiers can operate concurrently; drawer handover and cash movements are supported; new cash payments require an open drawer session; restaurant settings support cashier self-close and administrator/designated-replacement close. Proposed model: identify each drawer/session and bind each payment and cash movement to the intended open drawer. CS-01 enforces at most one open session per drawer. Whether drawers are assigned to a person, a workstation or a physical device, and detailed handover/replacement rules remain open; do not infer a permanent cashier–drawer assignment.

1. **Open.** An authorized staff member counts and declares the cash already in the drawer. The system records the amount, currency and opener; it does not assume yesterday's closing balance is today's float. Proposed access: existing staff; confirm who actually opens and supplies float.
2. **Collect.** Each cashier records full cash payments against the intended open drawer session, with the verified payment actor retained. Concurrent drawers do not share a balance. One committed payment has one matching attribution in the same transaction. A lost response is recovered with the original request identity. The current Billing slice records exact-received full cash, not tendered amount or change. Exact assignment and authorization remain to be decided.
3. **Move cash.** Record positive cash-in or cash-out with amount, reason, verified actor and time, such as float top-ups, supplier expenses and safe drops. Proposed first-release scope: a simple signed movement record with mandatory reason, no generic accounting engine. Operators must validate which movements occur, who can make them and whether approval or supporting references are needed. Cash-out should not be silently classified as a sale or refund. Correct an erroneous movement with a linked reversal/new entry, retaining the original; no deletion. Prevent duplicate recording on retry and define the treatment of withdrawals exceeding the calculated balance before contracts are approved.
4. **Close.** An authorized closer counts cash and records the count. Expected = opening float + cash sales + cash in − cash out; variance = counted − expected. Record a nonzero variance and explanation, not a fabricated zero. Sessions may cross midnight; closing is explicit. Example in consistent currency units: 1,000 opening + 5,000 sales + 200 top-up − 500 safe drop = 5,700 expected; 5,600 counted yields −100 variance.
5. **Handover.** User agreed: record outgoing and incoming cashier and count; a difference requires a reason. Administrators may arrange handover, including when the outgoing cashier is unavailable. The [candidate protocol](#candidate-business-rules-and-state) retains the actual initiator and any acknowledgment and requires incoming acceptance. No outgoing acknowledgment may be fabricated.
6. **Closing policy and unavailable closer.** User agreed administrators can always close; restaurant settings control cashier self-close and designated-replacement close. Initial values and replacement management remain open. Existing Access has staff and administrator only, so a narrow replacement capability needs design. Record the actual closer; do not auto-close or share credentials.
7. **Correct mistakes.** An authorized reviewer records a linked, attributed correction with reason; original close, count, payment and movement history remain visible. Correcting a count and correcting a payment assigned to the wrong session have different effects: the latter may affect both sessions and must never duplicate or alter the bill. Corrections after close need explicit adjustment/reconciliation semantics, authorization and evidence before the affected workflow launches. This is a product/operational launch blocker, not a claim that a first isolated backend increment must implement every correction.

Remaining product decisions: how drawers are assigned/selected, exact handover and unavailable-cashier recovery, closing settings and default, replacement designation and movement authorization. Operator validation is still needed for actual setup, movement categories, custody and correction practices. Revisit unconfirmed assumptions as evidence arrives; no need to delay all CS-00 design while arranging validation.

## Concrete proposal and remaining decisions

1. **Agreed 2026-10-28:** a cashier uses one drawer at a time; each drawer has one responsible cashier at a time and multiple drawers operate concurrently. Proposed safeguard: at most one open session per physical drawer. An administrator registers a bounded drawer label; permanent staff–drawer or workstation assignment is not assumed. These implementation details remain proposed.
2. **Agreed:** handover records outgoing and incoming cashier and the cash count; a difference requires a reason. An administrator can arrange handover, including when the outgoing cashier is unavailable. Proposed protocol: a current custodian or administrator initiates, and the eligible recipient counts and accepts; pending transfer freezes new cash activity. Save expected, actual, difference, initiator, outgoing and incoming identities, acknowledgments and time; preserve the session. If the outgoing cashier did not initiate or acknowledge, record that fact; never fabricate consent. Admin initiation is not recipient acceptance. Idempotency, cancellation and conflict semantics are candidate contracts below.
3. **Agreed:** administrators can always close; restaurant settings control current-cashier self-close and designated-replacement close. Self-close refers to the current custodian. Proposed design: administrator-managed `selfClose` and `replacementClose` settings and an explicit replacement set; staff cannot self-designate, and current account/branch authorization is rechecked. Initial policy/default, replacement scope and exact designation management remain unconfirmed. Do not add a general permission framework. Existing Access supports only staff/admin; a narrow scoped Shifts-owned designation checked inside `runAuthorized` is a candidate, not an existing Access permission.
4. Cash-in/out are positive amounts with reason and current actor. Recommend current custodian only; admin/replacement access and whether cash-out exceeding calculated balance is allowed remain decisions. A wrong movement needs a linked reversing movement; that correction is not implemented and blocks restaurant use. A refund is not an ordinary cash-out. Physical count or card acceptance is not proven by the API.
5. Close records expected, count and difference with actor/time and reason for a nonzero variance. Correction of mistaken close or misattributed payment is a launch blocker; this proposal does not silently authorize historical edits. Keep closed history immutable and develop a linked adjustment workflow separately before affected operation.

The confirmed always-admin close rule supersedes the earlier proposed configurable `administratorClose` option. This does not grant administrators a fabricated outgoing cashier acknowledgment during handover.

## Candidate business rules and state

- Drawer identity is server-generated, scoped to trusted business/branch, label unique within that branch, never a client-supplied authorization context. No physical drawer hardware control is implied. Open requires configured close policy, nonnegative opening amount, validated Business currency/scale and current staff access. Multiple separate drawer sessions may remain open. Each session has open/closed status, current custodian, monotonically increasing revision and optional pending handover; opening/closing and custody events record actor/time. Persist exact minor-unit decimal strings, bounded like Billing's 24-digit money. Reject totals beyond the chosen supported bound atomically; no floating point or truncation.
- A pending handover is created by current custodian or administrator with expected session revision and recipient. Recipient must be currently authorized in branch, have no other open custody, and accept using expected revision and counted cash. A nonzero difference requires reason. An administrator may initiate when the outgoing cashier is unavailable; the record identifies the actual initiator and does not invent outgoing acknowledgment. Initiation is not recipient consent. If the recipient loses access or is unavailable, cancellation by current custodian or administrator must be possible. No automatic expiration or acceptance is assumed.
- Handover acceptance is a physical-count assertion and does not change opening balance, cash sales or cash movements. Its difference is an observation, not a balance adjustment. On subsequent close, expected remains opening + attributed sales + cash-in − cash-out; do not add the handover count to the expected total. Any financial correction requires an explicit linked event. Proposed session revision increments on every state change; exact increment policy and overflow bound must be specified at contract approval.
- A close, movement, payment or handover uses current trusted scope, actor, account/grant status and session state. Pending handover blocks new money-changing operations. A committed retry may replay after status/custody changes under current authorization without recreating anything; do not confuse replay with permission to make a fresh mutation. Closure freezes admission, not history correction operations yet to be designed.
- No simultaneous write may bypass the same transaction/locking admission protocol. Preserve actor/time across handovers. Client-provided IDs choose an object within authorized scope; they do not establish role, owner or business. Current Access serialization is installation-wide: it serializes transactions briefly even across distinct drawers; it does not mean only one cashier can operate or be logged in.

## HTTP surface

CS-01 implementation decision: staff need to rediscover configured drawers after a restart to open an existing drawer. `GET /api/v1/cash-drawers` returns at most 100 scoped `{id,label}` entries, sorted by label and ID. Creation is capped at 100 per branch under the same authorized transaction. This bounded list avoids requiring a separate reporting or pagination feature; no drawer deletion or history listing is introduced.

CS-01 implements this bounded interface, with the adjustments noted below. All routes use `/api/v1`; scope/actor come from Access. JSON requests use strict DTOs, reject unknown fields and query keys; UUIDs normalized lowercase, timestamps UTC, amounts canonical decimal minor-unit strings. `currencyCode`/`scale` come from Business and are returned, not caller-selected. New business responses use `{data, meta:{requestId}}`, `Cache-Control: no-store`, correlation and existing Access origin/session/CSRF checks; mutations use POST or PUT. Use shared validation and Problem Details components. JSON media/adapter fallback limits are as in the [HTTP guide](../../../../../infrastructure/http/README.md). Drawer discovery is bounded as specified above. No search or history listing is provided.

| Candidate operation | Input / public result | Result and admission |
| --- | --- | --- |
| `GET /cash-drawers` | no query → bounded array of `{id,label}` | 200; staff; branch scoped, maximum 100. |
| `POST /cash-drawers` | `{label, retryKey}` → `{id,label}` | 200; administrator; bounded normalized branch-unique label, maximum 100 drawers. |
| `POST /cash-drawers/:drawerId/sessions` | `{openingMinor,retryKey}` → session view | 201 + Location; authorized staff; configured policy, drawer free, actor eligible. |
| `GET /cash-drawer-sessions/current` | no query/body → session view or `null` | 200; current actor's single open custody. |
| `GET /cash-drawer-sessions/:sessionId` | no query/body → session view | 200; scoped authorized custodian/admin or specifically approved replacement. Prior actors' historical read permissions require an explicit decision. |
| `POST /cash-drawer-sessions/:sessionId/movements` | `{direction,amountMinor,reason,expectedRevision,retryKey}` → movement view | 200 action response; current custodian only; reason and numeric bounds below. |
| `POST /cash-drawer-sessions/:sessionId/handovers` | `{recipientStaffId,expectedRevision,retryKey}` → pending handover view | 200 action response. Current custodian or administrator; no pending transfer; recipient eligibility checked at initiate and accept. Preserve actual initiator and any outgoing acknowledgment. |
| `POST /cash-drawer-sessions/:sessionId/handovers/:handoverId/accept` | `{countedMinor,varianceReason,expectedRevision,retryKey}` → updated session view | 200; named recipient, recheck access and expected revision. A nonzero difference requires a reason. |
| `POST /cash-drawer-sessions/:sessionId/handovers/:handoverId/cancel` | `{expectedRevision,retryKey}` → updated session view | 200; initiating custodian or administrator; pending only. Administrator recovery is a separate action and contract, not implied by cancel. |
| `POST /cash-drawer-sessions/:sessionId/close` | `{countedMinor,varianceReason,expectedRevision,retryKey}` → closed session view | 200; currently authorized closer according to saved policy. Pending handover cannot be silently bypassed; recovery design remains open. |
| `GET /cash-drawer-policy` / `PUT /cash-drawer-policy` | GET → policy view; PUT `{selfClose,replacementClose,replacementStaffIds,expectedRevision,note}` → policy view | 200; staff read/admin write, validated account/branch grants and bounded set; proposed maximum 100 replacements, revision-checked full replacement, audit actor/time and prior/new values. Administrator close is always allowed by policy, subject to current Access authorization; it is not a configurable field. Visibility and initial values remain open. |

Common fields proposed: UUID `retryKey`, unique per business/branch/operation and retained with resulting event/history; `expectedRevision` integer 0–2,147,483,647; `amountMinor` positive and opening/count nonnegative canonical decimal string, maximum 24 digits; `reason` trimmed nonempty string up to 500 Unicode code points; `varianceReason` null or such a string. Exact Unicode normalization and aggregate bounds are design decisions to finish, not an implemented validator. Identical normalized key/request returns its original stored selected result; same key with changed content gives 409. Once authorized, replay precedes session revision/state/policy checks; denied or failed transactions retain no successful key. Keys cover all affected path identities and request fields; a key is never regenerated after timeout. Revision conflicts give 409; policy PUT uses expected revision and readback after timeout, rather than pretending it has a durable retry key. A stable per-operation retry result prevents changed current state from altering a replay; select minimal actor and financial fields, never credentials, customer information, raw retry keys or SQL.

Candidate session view: `{id,drawerId,status,currencyCode,scale,openingMinor,openedAt,openedBy,currentCustodianId,revision,pendingHandover,closed}`; `pendingHandover` is null or `{id,recipientStaffId,initiatedBy,initiatedAt}`; `closed` is null or `{countedMinor,expectedMinor,varianceMinor,varianceReason,closedAt,closedBy}`. Signed variance uses canonical signed integer with no negative zero. Movement view `{id,sessionId,direction,amountMinor,reason,actorId,occurredAt}`. Policy view `{revision,configured,selfClose,replacementClose,replacementStaffIds}`; names are candidates, not canonical schemas. Which roles can see financial totals and personnel IDs remains a product/access decision; choose safe projections before implementation. No aggregate collection or unbounded event list is specified.

Proposed shared failure mapping: malformed/unknown fields 400 `/problems/validation-failed`; unavailable or unauthorized scoped objects 404 where disclosure would leak existence; unauthorized action 403; state, duplicate-content mismatch, wrong custodian, pending handover, stale revision or old session 409 with stable named problem types; unknown infrastructure failure 500 and known temporary unavailability 503 with safe correlation. Exact problem codes/allowed extensions, media/body ceilings and inaccessible-object consistency still need endpoint review. No client input, money, secrets or raw exception is echoed by default. Do not promise adapter-level/unmatched-route errors use the shared contract.

## Billing compatibility and transaction options

The [compatibility matrix](#proposed-billing-compatibility-matrix) remains the cross-module review baseline. Recommended compatible migration candidate: accept the legacy eight-field DTO and a new version containing `sessionId`; normalize each shape distinctly before authorization. In the single authorized transaction look up the existing scoped retry key first. For a historical legacy record, compare exactly as today and return its saved BillView/201/Location. For a new-shape successful record, compare all original fields plus session identity; identical replay succeeds under current authorization regardless of later handover/close, changed content conflicts. A legacy-shape request without an existing successful key fails with an actionable missing-session conflict before any new bill. After lookup of a new-shape request, check its session is open, not pending handover, owned by currently authorized custodian, and matches currency; then persist bill plus attribution atomically.
