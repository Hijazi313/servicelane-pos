# Kitchen handoff — proposed specification

Date: 2026-10-22. Reviewed: 2026-10-23. Status: technical specification proposed; KT-D01–04 business boundaries approved for development. [Tracker](phase-tracker.md); [decisions](decisions.md); [global tracker](../TRACKER.md).

## Outcome and smallest justified scope

Propose **KT-01: explicitly dispatch one captured takeaway order into a durable branch kitchen queue and advance the whole ticket through preparation to ready**, exposed through the backend only. This is phase P0 for demonstrating a durable Orders → Kitchen handoff, not product MVP completion or permission for restaurant use. KT-D01 approves explicit dispatch without a payment prerequisite for this development slice.

A queue alone would expose work without preparation progress; ready is this development slice’s endpoint, with operational collection/completion still deferred. Conversely, printers, a screen UI, station routing and line-level scheduling are not needed to prove this backend handoff. Do not add a general event bus, workflow engine or background delivery worker for an in-process transaction.

| Requirement | Phase P0 justification / simpler alternative |
| --- | --- |
| KT-R01: Explicit authorized, duplicate-safe dispatch | An operator decides when a saved order becomes preparation work; automatic capture dispatch is a material alternative considered in KT-D01. Repeated/lost-response dispatch must not prepare twice. |
| KT-R02: Complete immutable preparation snapshot | A cook needs quantities, variants, extras, combo composition and instructions; names from current Menu could change an accepted order. Full Orders payload unnecessarily discloses customer/financial data. |
| KT-R03: Durable scoped pending queue and single-ticket read | A missed response or reconnect must rediscover committed work. Memory-only state cannot establish the handoff. A bounded pull interface is sufficient; no push transport required. |
| KT-R04: Whole-ticket state with deliberate conflicts | Kitchen must distinguish waiting, started and ready. A single ready boolean loses whether preparation began; richer line/station lifecycles have no current requirement. |
| KT-R05: Preserve Orders meaning and isolation | Kitchen state cannot imply payment, fiscal sale, collection or order amendment. Scope/permission checks must reject unauthorized and foreign data. |

## Source baseline and ownership

Accepted [Orders capabilities](../../../apps/api/src/modules/orders/docs/capabilities.md), [Menu](../../../apps/api/src/modules/menu/docs/capabilities.md), [Authentication](../../../apps/api/src/modules/authentication/docs/capabilities.md) and [Business](../../../apps/api/src/modules/business/docs/capabilities.md) were consulted. Orders [public.ts](../../../apps/api/src/modules/orders/public.ts) exports only OrdersModule. [OrdersService](../../../apps/api/src/modules/orders/application/orders.service.ts) provides capture/read/policy internally; [OrderStore](../../../apps/api/src/modules/orders/application/order-store.ts) stores immutable snapshots with customer and merchandise fields. No dispatch, queue or lifecycle interface exists in those reviewed exports. No Kitchen module/index exists. These are source facts, not new runtime evidence.

Proposed source work must add a narrow Orders-owned application operation and matching public/provider exports. It accepts the existing trusted AuthorizedScope and order ID, reads its own snapshot in that active transaction and returns only the approved preparation projection. Do not export OrderStore, its rows, full OrderSnapshot or HTTP controller as Kitchen's interface; do not re-resolve current Menu. Orders retains identity/history/composition ownership. Kitchen owns the ticket, dispatch metadata, revision and preparation state. Authentication `runAuthorized` owns current session/grant/role/CSRF and transaction coordination; Business remains owner of installation/branch settings. No new business identities or hardcoded restaurant settings.

Two concrete prerequisite extensions belong inside proposed KT-01, not implied existing capabilities:

- Orders `OrderStore.get` / `PostgresOrderStore.get` currently read through the root database handle and accept no transaction. Add a transaction-aware Orders-owned preparation read behind its public operation; use the supplied opaque transaction in its adapter. Do not call current `OrdersService.get` (which authorizes separately) or let Kitchen query Orders tables. Existing HTTP capture/readback semantics remain unchanged.
- Authentication `AuthorizedScope` currently contains only installation and transaction, although `runAuthorized` validates an account. Expose only that verified account’s ID as trusted mutation actor in the callback scope, without credentials, session proof or account profile. This additive Authentication public-contract change and affected consumer fixtures/docs are part of the proposed source boundary; no nested `me` call, client actor input or foreign Authentication persistence. Persist dispatch and each of the two transitions with separate retained actor/time stamps (internal provenance; preparation responses need not expose staff identity); do not overwrite earlier stamps or introduce a general audit subsystem. Existing consumers must remain compatible.

## Proposed contracts and failure behavior

These are semantic contracts, unavailable and unapproved; final schemas/routes belong to later source work after decisions. No API spelling or implementation is approved by this plan.

- Dispatch takes an existing order ID, not client-supplied preparation content, branch, status or payment proof. One staff-policy authorized transaction calls the Orders projection operation and commits one Kitchen ticket initially queued. All reads/writes are awaited in the same transaction; no nested authorization, extra connection or external I/O. An atomic uniqueness constraint on trusted business/branch/order identity makes one ticket per order. Concurrent repeats or a lost response return the same ticket in its current state without resetting it. Rollback leaves no ticket; captured order remains readable.
- Tickets carry a stable ticket ID, source order ID, server timestamps, actor identity for mutations, revision and an immutable preparation projection. Preserve source line order and stable line position plus full selected composition; do not turn combo components into independently ordered quantities. Project captured `unit.name`, `unit.components` identities/names/per-unit quantities, `unit.addOns` IDs/names and `unit.choices` group/option IDs/names using an explicit nested allowlist: extras and choices currently contain surcharge fields that must be omitted too. Keep line quantity separate; required component units equal line quantity × component per-unit quantity. For example, three combos with two identical components per combo require six components; do not add the choice labels as extra components because Menu already includes selected choices in `unit.components`. No current Menu lookup is needed. A changed/deactivated Menu cannot change dispatched content. Do not copy customer fields or money into Kitchen storage or responses.
- Read one full ticket by ID. List only bounded summaries (ticket/order IDs, capture/dispatch times, state and revision), with full preparation content obtained by the ticket read; this avoids multiplying Orders’ up-to-1 MiB snapshots into one page. Proposed technical bounds: default 25 summaries, maximum 100; maximum serialized full-ticket response 1 MiB, checked at dispatch before commit including all bounded future transition stamps. Reject capacity overflow without a ticket rather than truncate preparation content or change Orders capture limits. Invalid/foreign IDs and unavailable/inconsistent snapshots fail without committing work; no “best effort” partial ticket.
- List all current-branch queued/preparing/ready tickets without status filtering or deletion in this slice. Ready remains outstanding until a separately approved completion/collection boundary exists. Paginate by a unique immutable increasing dispatch position assigned in Kitchen persistence while the existing installation-wide authorized mutation lock is held; gaps after rollback are harmless. Wall-clock timestamps are display metadata, not pagination order. First page fixes the highest committed scoped position as a scan fence; continuation reads positions strictly after the previous page and at/below the same fence. New dispatches belong to the next scan. Cursor contains only validated bounded position/fence data (0 ≤ last position ≤ fence, with fence no higher than the current committed scoped maximum), never trusted ownership; every page reauthorizes the current session/branch and re-applies trusted scope. A cursor from another branch grants no access. This is keyset enumeration of a finite durable set, not an event log or a cross-page state snapshot: re-scan from the first page after reconnect to refresh statuses and discover later tickets. No event stream, offset paging or long-held scan transaction. If source entry changes the shared mutation serialization, re-evaluate visibility ordering before relying on a sequence fence. A growing ready backlog and absent capture-order search remain explicit development limits; dispatch consumes the ID returned by Orders capture/readback rather than adding an Orders list API.
- Status starts at queued/revision 0. Requests supply target state and expected nonnegative integer revision (bounded to this two-transition lifecycle). Atomically permit only queued/0→preparing/1 and preparing/1→ready/2, retaining each verified actor/time stamp once. An exact repeated target with the immediately preceding expected revision returns the unchanged current ticket without another stamp, even when another authorized staff member requests that same outcome; this is state idempotence, not proof of who originally issued a request. For example preparing/expected 0 succeeds idempotently while current state is preparing/1; after ready/2 that delayed request conflicts and returns current scoped state/revision for refresh. All other stale, skipped or backward changes conflict. No persistent mutation retry key or generic history is needed for these two forward-only transitions. Dispatch retries likewise return the current ticket and never reset state, position, timestamps or original attribution.
- Invalid input rejects before mutation; absent/foreign order or ticket IDs return indistinguishable not-found. Current unauthorized/revoked/branch-denied access fails without disclosing content or writing work. Reuse shared access boundary, keep semantic errors in application/domain and map HTTP status only in HTTP. Bound request/page/response sizes using existing safeguards; reject unsupported fields and avoid instruction/customer data in logs/errors.

## Acceptance criteria

Criteria remain proposed pending technical specification review; KT-D01–04 business boundaries are approved. Future evidence must use synthetic data and separately authorized verification; no checks are run by planning.

| ID | Scenario and required observable result | Expected future evidence |
| --- | --- | --- |
| KT-A01 (R01/R05) | Dispatch a captured order under current authorized scope; exactly one scoped queued ticket is committed and the original captured snapshot remains unchanged. Invalid/revoked/grant-denied and foreign-ID requests disclose/write nothing. | Focused API/application checks plus separately authorized persistence isolation case |
| KT-A02 (R01) | Concurrent dispatch, lost-response retry and retry after preparing/ready produce the same one ticket without state reset. Injected failure leaves no partial ticket and the order readable. | Bounded real persistence concurrency/rollback verification, permission pending |
| KT-A03 (R02) | Sized item with extras and repeated combo choices, quantity greater than one, order/line instructions preserve exact captured preparation meaning after Menu rename/deactivation. Customer/financial/policy/retry fields, including nested add-on/choice surcharges, are absent from Kitchen records and responses; verify the three-combo/two-component example yields six units. | Synthetic projection/API checks; fixture includes personal-looking text only to verify explicit free-text policy, never real customer data |
| KT-A04 (R03) | List multiple summary pages with a fixed fence while new dispatches/status changes occur; each pre-fence ticket occurs once, later dispatches appear in a fresh scan, and statuses refresh on rescan. Read complete preparation content after reconnect/fresh API process. Backward wall-clock changes cannot skip tickets. Oversize pages, malformed cursors and foreign IDs disclose nothing; response-capacity rejection leaves no ticket. | Focused boundary checks and separately authorized fresh-process persistence readback; no crash/backup recovery claim |
| KT-A05 (R04) | Advance queued→preparing→ready; race two revisions, repeat a successful transition and attempt skip/backward/stale changes. One logical transition wins; immediate same-target retry preserves the original actor/time and delayed retry after further advancement conflicts. Distinct dispatch/start/ready actor/time stamps and revisions survive persistence readback; attribution checks use owned persistence evidence without adding staff profiles to preparation responses. Client actor input is rejected. | Focused semantic/API checks plus separately authorized atomic-update concurrency case |
| KT-A06 (R05) | Capture without dispatch creates no ticket; preparation changes do not mutate Orders, Menu, payment/tax or stock. Edit/cancel/delete/replacement requests remain unsupported. | Focused contract/boundary inspection and behavioral checks; automatic dispatch would require an explicitly approved future specification change |

## Deferred scope and release gates

P1 for this development phase: KDS/browser UI and live push (pull proves the backend handoff), printer/bridge/station routing (no physical output required), partial/line preparation, priorities/ETAs/analytics, multi-branch operation, reprints and generic integration infrastructure. P1 classification here does not settle their MVP necessity.

Amendment/cancellation, completion/collection and payment-ordering are material workflow decisions, not disposable conveniences. They need approved later scope before restaurant use; no implementation is activated here. Customer retention/access policy, fiscal applicability, production TLS, recovery and provisioning remain under existing [compliance guidance](../../compliance/README.md) and accepted upstream evidence limits. No new legal requirement, tax exemption or retention period is asserted. Kitchen ready never means paid, served or fiscally finalized.
