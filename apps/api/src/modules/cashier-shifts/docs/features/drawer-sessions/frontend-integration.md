# Cashier Shifts — integration guide

CS-01 provides isolated backend source, not activated routes. [Phase tracker](phase-tracker.md#current-handoff) records bounded PostgreSQL verification, user acceptance and remaining release gates. [DTOs](../../../http/drawer-input.dto.ts) are the canonical input structures; [controller](../../../http/drawer.controller.ts) defines routes. Business and branch are resolved by Access, never supplied by the client. All mutations require the existing origin/session/CSRF boundary; staff reads do not require CSRF. Responses use the shared `data` envelope, correlation ID and no-store headers.

Administrators configure close policy and create drawer labels. Staff can list up to 100 branch drawers, open a free drawer with a counted opening amount, and discover their current session. Money is a canonical decimal string in minor units; currency and scale come from Business. A staff member may hold one open drawer at a time. Movements require a positive amount and reason; cash-out cannot exceed expected cash. Session mutations carry the current revision. A pending handover freezes money-changing operations until the named recipient accepts or the custodian/administrator cancels it. Acceptance records a count and a reason for any difference; it does not adjust the expected balance. Closing requires a count and a reason for a nonzero difference. Administrators may close; configured settings govern self-close and designated replacement close.

For every mutation with `retryKey`, generate and retain a UUID and the complete original normalized request until its outcome is known. On timeout, repeat the same request and key; changed input with the same key conflicts. Current access is rechecked on replay. Policy replacement uses expected revision and readback instead of a retry key. Drawer and movement creation return 200 because there is no stable individual resource GET; opening returns 201 and a session Location. Known-session reads are limited to current custodian, administrator or an enabled designated replacement. Read authorization and the subsequent storage read are separate operations, as in existing Billing readback; ordering against concurrent revocation is not verified.

New Billing cash settlements must supply `sessionId`. A previously successful legacy request without it can still be retried unchanged; a fresh legacy request gets `CASH_DRAWER_REQUIRED`. Replaying a successful session-bearing settlement after closure returns the original bill and never reattributes it. A new request to a closed, transferred or incompatible session fails. Existing clients need coordinated updates before new payments. [Billing contract](../../../../billing/docs/features/settlement/spec.md#cs-01-settlement-admission-migration) owns its detailed semantics.

The source does not supply history-preserving correction for a mistaken movement, closed count or wrong-session payment. Those, physical cash handling, fiscal/receipt requirements and operational recovery remain release blockers. Migration, rollback, concurrency and fresh-process readback passed bounded PostgreSQL tests on one disposable target; this is not restaurant-readiness evidence.
