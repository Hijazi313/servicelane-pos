# Authentication and Access — Specification

## Outcome and provenance

Restaurant administrators provision and control staff accounts; staff log in locally and perform only authorized actions for the installation's business and permitted branch. Internet loss does not introduce a mandatory cloud login dependency.

[Architecture policy](../../../../../../../../docs/architecture/README.md#business-branch-and-access-foundation) establishes staff lifecycle, secure credentials, sessions, disabling/revocation and server-enforced access as product P0. The user subsequently approved BA-D01/BA-D02/BA-D05, including identity, credential and fixed-role direction. BA-01 implements initial administrator persistence only. User subsequently approved the complete BA-02 review design and authorized source implementation of BA-02-T01/T02/T03. Authorization does not cover database execution, installation or deployment.

## Approved P0 requirements

| ID | Requirement | Why needed / simpler alternative |
| --- | --- | --- |
| AA-R01 | Controlled administrator bootstrap and authenticated staff lifecycle | Accounts must be created, corrected, disabled and recovered without public signup/manual database edits. Reuse joint provisioning; no invitation/email service. |
| AA-R02 | Local username/password login with adaptive password hashing and abuse controls | LAN clients still need identity; plaintext/reversible passwords and unrestricted guessing are unacceptable. No external identity service or short shared PIN login. |
| AA-R03 | Server-controlled sessions, logout, expiry and prompt revocation | Disabled staff and stolen sessions must lose access. Propose opaque sessions with server state rather than a stateless token plus revocation framework. |
| AA-R04 | Default-deny business, branch and action authorization on every protected operation | Client IDs and hidden UI do not enforce permissions. A fixed small role matrix is simpler than a permission designer. |
| AA-R05 | Recover access locally with attributable privileged operations | Email/internet recovery would break the approved topology. Operator command requires host-level authorization, never an unauthenticated recovery endpoint. |

## Approved identity and role rules

- Own staff account `{id, businessId, username, displayName, status, role}`, credential hash, explicit branch grant, server sessions and minimal security-event records. Business IDs must match the installation; branch grants must pass Business ownership validation. Never cascade-delete business history when disabling staff.
- Proposed roles are `administrator` and `staff`. Both may read their authorized context, change their own password and log out. Only administrators may list/create/edit staff, change role/grant, disable/re-enable accounts and initiate managed password reset. Neither role has implicit permissions in Menu, Orders or Payments; their modules will add explicit action policy later.
- Initially grant the one operational branch explicitly, including to administrators. No implicit access to every future branch. Reject role or branch-grant input not defined by this specification.
- Propose usernames normalized to lowercase ASCII, 3–64 characters from letters, digits, dot, underscore and hyphen, unique within the installation. Passwords are never trimmed or silently truncated. Propose passwords of 15–128 characters, permitting spaces/Unicode, without composition rules or routine forced rotation; validate length consistently. Hash using a maintained Argon2id implementation, with cost parameters reviewed against current guidance and measured on the target host before release. No library installation is authorized by this document.
- Do not allow disable/demotion of the last active administrator. Serialize concurrent admin-removal attempts. Failed operations leave account/grant/session state unchanged. Re-enabling never restores revoked sessions.
- Account creation/reset uses a password entered over a protected channel; propose forced password change before any ordinary operation. That restricted session may only change password or log out. A password change must reject an unchanged current/new password with 400 before any credential/session mutation. A valid password change rotates session identity and revokes all other sessions. Reset/disable/grant or role changes revoke existing sessions within the same account-change transaction.

## Approved session and failure rules

- Same-origin browser client and API over trusted LAN HTTPS; opaque random session in a Secure, HttpOnly, SameSite cookie, with no broad Domain setting. Store only a token digest server-side, bound to this installation/account. No browser local-storage bearer token. Session fixation must fail; always issue a fresh token after login/password change.
- Propose 30-minute idle and 12-hour absolute expiry, enforced by the server clock. No remember-me or concurrent-device limit in this increment; logout revokes the current session. Disable/reset revokes all sessions. After a revocation transaction commits, subsequent authorization checks fail; requests already authorized may finish. Sensitive staff administration rechecks authorization in its mutation transaction so concurrent privilege revocation cannot be bypassed.
- Verify current account status, branch grant and action permission on every protected request; never trust cached client role. Persistence failure denies access rather than falling back to cached authority. Revoked/expired/foreign-installation session returns 401; authenticated insufficient action permission returns 403. Scope-sensitive missing/foreign resource returns 404 without identifying another business.
- All state-changing cookie-authenticated requests require CSRF protection, including login/logout: validate allowed Origin and a server-issued CSRF token; use safe methods only for reads. Restrict credentialed origins to configured client origin, never wildcard. Propose a public same-origin CSRF-token bootstrap operation that exposes no business data.
- Invalid, unknown and disabled-account login returns the same generic 401. Use bounded account-key and source-address throttling with fixed windows and immediate 429, without permanent lockout or exposing account existence. The BA-D03 recommendation below defines thresholds, shared persistence and restart behavior; no Redis or external CAPTCHA dependency.
- Security events record actor/target IDs, action, timestamp, success/failure and local operator identity where applicable; never passwords, raw session/CSRF tokens or request bodies. Logs are protected locally; retention and operator identity custody must be settled before deployment.
- Credentials/sessions never travel over plain LAN HTTP. Restoring a backup must invalidate pre-restore sessions before serving traffic; production recovery design owns the exact procedure. Automatic restore/failover is outside this phase.

## HTTP interfaces

Executable input validation and route mappings live in [access-policy.ts](../../../application/access-policy.ts), [access.service.ts](../../../application/access.service.ts) and [access.controller.ts](../../../http/access.controller.ts). New routes use `/api/v1` before every suffix below; technical `/health` stays unprefixed. Source is implemented, with runtime acceptance pending. Public endpoints are narrowly justified: technical `/health` remains as accepted; login and CSRF bootstrap allow authentication. Staff management and context require authentication.

| Operation | Inputs | Outcome |
| --- | --- | --- |
| `GET /auth/csrf` | Same-origin browser bootstrap | CSRF token and matching protected state; no account/business data |
| `POST /auth/login` | Username, password, CSRF proof | Session cookie; safe account ID, role, permitted branch and password-change-required flag; no token in JSON |
| `POST /auth/logout` | Session/CSRF | 204 and expired cookie; repeated logout succeeds without restoring a session |
| `GET /auth/me`, `GET /context` | Session | Safe current identity and authorized installation context; never credential/hash/session internals |
| `POST /auth/password` | Current and new password; session/CSRF | Change credentials, rotate current session, revoke other sessions; forced-change restriction cleared |
| `GET /staff`, `POST /staff` | Administrator; create uses username/display name/role/branch/password | Business-scoped safe list or created identity; duplicate username 409 |
| `PATCH /staff/:id` | Administrator; explicit allowed display/role/grant/status fields | Updated safe identity; restricted fields rejected, changes revoke sessions |
| `POST /staff/:id/password-reset` | Administrator and securely supplied temporary password | Force password change; revoke all sessions, no password echoed |
| Operator `recover-administrator` | Explicit local business/account, verified operator identity and securely entered replacement password | Recover an existing administrator, revoke sessions and require change; no public endpoint or universal bypass credential |

Use 400 for invalid input, 401/403/404 as above, 409 for conflicts/last-administrator removal, 429 for throttling and sanitized 503 for unavailable persistence. Do not disclose raw SQL, credentials or foreign existence. No hard delete or arbitrary bulk staff export. The privileged operator command is outside normal HTTP role permissions and requires a separately approved operational runbook; application source cannot prove host access was authorized.

## Acceptance examples

### AA-AC01 — Staff lifecycle and permissions

Bootstrap an administrator through BB-AC02. Create staff, require initial password change, then read context. Staff cannot list/create/manage another account, set an arbitrary role or change their own grant. Admin can edit/disable/re-enable permitted staff; last-active-admin removal and concurrent removal are rejected. Inspect persisted credentials: hashes only, no password returned or logged. Evidence: focused credential/authorization checks and user-run local lifecycle; hash source review is not a login result.

### AA-AC02 — Login and browser session

Correct credentials create a fresh session; wrong password, unknown username and disabled account give the same generic response. Throttle under the agreed policy. Cookies have agreed protections; no raw token in response body/logs. Expired, forged and installation-B sessions fail on A. Missing/invalid CSRF and unapproved origins cannot mutate state or establish a session. Evidence: HTTP/cookie checks and browser acceptance on trusted HTTPS once separately authorized; source review alone does not establish browser behavior.

### AA-AC03 — Revocation and concurrency

Log in on two devices. Logout revokes one; password change/reset/disable/role or branch-grant change invalidates the required sessions. Following commit, the next request is rejected; re-enable does not resurrect a token. Exercise sensitive-admin mutation racing with revocation and verify transactional recheck. Test idle/absolute expiry with a controllable clock. Evidence: focused session/integration behavior, not assumptions from token contents.

### AA-AC04 — Local recovery and denial on failure

Authorized operator recovers an existing administrator without internet or manual SQL; old sessions/password fail and replacement requires change. Record safe operator event. Ordinary staff/unauthenticated HTTP cannot invoke recovery. Database outage causes login and protected operations to fail closed with sanitized errors. Host operator authorization and backup session invalidation need operational evidence before release.

### AA-AC05 — Business and branch isolation

User A must not access B by replaying cookies or changing business, account or branch IDs. Reject an ungranted branch belonging to the same business as well as a foreign branch. Use a focused disposable fixture for non-operational branch cases when database writes are separately authorized; this does not activate multi-branch product operation. Ensure unprotected routes are limited to the stated exceptions, including proof-validated idempotent logout.

Under the user-approved 2026-10-17 scope revision, BA-03 development acceptance combines existing service/double checks for foreign account IDs, session-business mismatch and branch references; source review of business-scoped lookups, fixed database selection and route policy/default denial; and actual single-database HTTP checks for unsupported identity fields, unknown account/branch references and an existing same-business ungranted branch. Retain fail-closed context/persistence behavior under BB-AC04. Existing evidence may be reused with its type/limits stated; this does not require another execution. Actual reciprocal replay of real cookies/IDs between two provisioned installations is **deferred, unrun**, to future installation/provisioning validation; the isolation requirement remains. ## BA-02 implementation-review design — 2026-10-12

User approved this complete review design and authorized BA-02 source implementation on 2026-10-12. Database/browser/operational acceptance remains separately authorized. Existing BA-01 approvals and evidence remain intact. Numerical limits are project defaults, not compliance mandates.

### BA-D03 — Session, CSRF and bounded login work

- Generate 32 random bytes for each session token. Store its SHA-256 digest, account/installation binding, creation/last-activity times and revocation state in Authentication-owned PostgreSQL tables. Use `__Host-session`, Secure, HttpOnly, SameSite=Strict, Path=/, no Domain. Enforce 30-minute idle and 12-hour absolute expiry on every authorization check; only successfully authenticated requests refresh idle time. No persistent browser cookie, remember-me, JWT or device cap. Rotate on login and password change; revocation semantics above apply.
- Use a server-side synchronizer CSRF token. Bootstrap creates a random pre-login cookie and matching short-lived PostgreSQL state (10 minutes); return a separate random token in no-store JSON. Login requires this cookie/token pair and exact configured Origin, then destroys pre-login state and creates a fresh session and session-bound CSRF token. Return that CSRF token on login and authenticated bootstrap; never put session tokens in JSON. Validate `X-CSRF-Token` and exact Origin on every mutation, including login, logout and password changes. Missing or `null` Origin fails 403; no Referer fallback. GET/HEAD never mutate business data. No wildcard CORS or cross-origin credential support. Bootstrap responses are no-store, emit no permissive CORS headers, and reject an explicitly foreign Origin; initial same-origin GET may lack Origin. Expired logout remains idempotent only after valid pre-login/session CSRF proof; absence of a session is not a CSRF bypass.
- Replace progressive delays with fixed windows and immediate 429 plus Retry-After: simpler, with no sleeping requests. Per normalized username, reserve up to five credential attempts in a 15-minute window; failed attempts retain their reservation, success clears completed failures while preserving other pending attempts. Each admitted attempt has a random UUID reservation in the account row (at most five); settlement removes only that ID, is idempotent, and ignores expired/replaced windows. Pending attempts count, so concurrency cannot bypass the cap. Hashing errors and failed final-login transactions settle as failures. Worker-crash reservations remain charged until the existing 15-minute window expires. Per source address allow 30 login requests/minute including successful attempts; excess requests do not run hashing. Windows start on first attempt and expire without extension by rejected traffic. Apply identical account counters and dummy-hash work to unknown/disabled identities; generic credential failure is 401. No permanent account lock. Shared-device address limits allow multiple accounts but must be load-checked before release.
- PostgreSQL owns atomic counter reservations across workers/restarts. Key usernames by digest rather than retaining arbitrary submitted identifiers; canonicalize source addresses. Reject invalid/oversized bodies before hashing, and use a bounded hash executor (initially two concurrent hashes per process, no waiting queue; saturated requests get 429). No arbitrary PHC cost parameters: accept supported bounded algorithm/parameter/salt/hash formats only. Bound source rows and account rows to 10,000 each per installation; reject new keys at capacity with 429 until expired rows are removed. Bounded periodic cleanup deletes expired counter/pre-login/session records; expired state never grants access even if cleanup is delayed. Persistence failure returns sanitized 503 and never bypasses throttling. Source address comes from the socket by default; forwarding headers count only behind explicitly configured trusted proxy addresses, never blanket trust.
- Operational release verification AA-AC02/03 must cover exact threshold/window boundaries, parallel reservations, unknown/disabled identities, shared source with multiple accounts, restart/shared-worker persistence, capacity/cleanup, executor saturation, session fixation, CSRF bootstrap/login/rotation/logout and cookie attributes. Clock-controlled tests establish expiration without waiting hours. Target-host hashing latency/memory and shared-device usability remain release evidence gates.

### BA-D04 — Origin and HTTPS acceptance boundary

- One configured canonical origin per installation, including scheme/host/port; production requires HTTPS. Serve browser assets and API through that origin; future web development uses a same-origin development proxy. No separate-origin CORS mode in BA-02. Validate configured origin and request Host against the expected authority; reject foreign Origin on mutations independently of Host. This closes origin policy without selecting a frontend framework or provisioning a server.
- Production recommendation: installation-specific LAN DNS hostname, reverse proxy serving local assets and terminating TLS, certificate issued by an operator-managed local CA trusted on every client. API is reachable only through that proxy on the LAN; any plain HTTP upstream stays on loopback. Certificate issuance, trust distribution/renewal, hostname, proxy firewall and asset hosting require a separate deployment assignment/runbook. They are not BA-02 backend work or already verified capabilities.
- BA-02 source completion can use Fastify request injection to verify secure cookie/header/configuration behavior without weakening production cookies. Such checks do not prove browser cookie delivery, certificate trust or offline LAN operation. Current delivery is API-only, with no browser client or production HTTPS setup. AA-AC02 browser-delivery checks are not applicable to current BA-02 acceptance; scope them if a browser client is introduced. No plain-LAN-HTTP fallback or Secure-cookie bypass. The user’s [2026-10-17 revised acceptance](../../../../../../../../docs/planning/business-access/phase-tracker.md#ba-02-acceptance--2026-10-17) closes the backend development increment using source and scoped staging evidence, with browser/client HTTPS verification applicable only to separately scoped future browser delivery. BA-03 scope/acceptance is governed by the later joint-tracker records.

### Service placement and password adapter

Pre-BA-02 source review: `AdministratorProvisioner` lived in infrastructure and combined use-case validation, Business public calls, hashing and Drizzle writes. This worked for the accepted bootstrap slice but should not become the pattern for HTTP authentication. In BA-02 put lifecycle/login/recovery coordination in Authentication `application/`, persistence and crypto implementations in its `infrastructure/`, and controllers/guards/transport validation in `http/`. Move bootstrap orchestration behind the same application boundary while preserving its public capability, single shared transaction and BA-01 regressions. Introduce only the persistence/hash ports these use cases actually need; no generic repository or access engine. Business ownership continues through Business public operations; shared transaction coordination remains technical infrastructure. Wire Nest providers through the module, without exporting private persistence or creating circular imports.

Keep the existing Node Argon2id adapter for BA-02 development rather than install another native dependency solely to avoid an experimental label. Add bounded PHC verification, timing-safe digest comparison, controlled malformed-hash failures and compatible hash creation behind one private application-facing hashing port. Existing parameters are 19 MiB/two passes/one lane, 16-byte random salt and 32-byte output. Verify existing BA-01 hashes without rewriting them. No silent algorithm switch or credential reset. Node's API remains experimental: pinned-runtime compatibility, known-vector/old-PHC verification and target-host cost/concurrency measurements are mandatory before release; failure requires a reviewed maintained adapter replacement preserving stored hashes. This explicitly accepts development risk, not production readiness.

Guidance checked for this review: [Node 24 crypto Argon2](https://nodejs.org/docs/latest-v24.x/api/crypto.html#cryptoargon2algorithm-parameters-callback), [OWASP CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html), [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [Nest OpenAPI](https://docs.nestjs.com/openapi/introduction). ## Source contract details — BA-02

All bodies are JSON, with a 16 KiB transport limit and explicit allowed fields; extra fields are rejected. UUIDs are canonicalized to lowercase. Create requires `username`, `role`, `branchId`, `password`; optional `displayName` defaults to username. Patch permits only nonempty subsets of `displayName`, `role`, `branchId`, `status`. Password change uses `{currentPassword, newPassword}`; administrator reset uses `{password}`. There is no username mutation, arbitrary branch list, client-selected business ID, hard delete or bulk export.

Safe account responses contain `{id, businessId, username, displayName, status, role, branchIds, passwordChangeRequired}`. Login and password change return `{account, csrfToken}` and Set-Cookie; CSRF bootstrap returns `{csrfToken}` with a pre-login cookie when necessary. Tokens/password hashes never appear in account JSON. Create returns 201, other reads/patch/login/password change 200, logout/reset 204. Errors use `{statusCode, message}`, with Retry-After for 429 and no raw exceptions. Malformed body/identity/password fields return 400; well-formed wrong/unknown/disabled credentials share 401. No permissive CORS headers are emitted.

Forced-change sessions permit password change/logout and the supporting CSRF bootstrap only; ordinary `/auth/me`, `/context` and staff operations return 403. Session bootstrap is not a business-data read. Invalid session bootstrap can issue fresh pre-login state without authenticating the caller. An active session requires its own session-bound CSRF proof for logout; a valid pre-login proof cannot substitute. Successful logout revokes that active session before cookies are cleared. For repeated logout after browser cookies are cleared, obtain fresh pre-login CSRF proof; retained revoked/expired session proof also permits idempotent logout until cleanup removes that state. Cleanup cannot restore authority.

`CLIENT_ORIGIN` is required for HTTP startup and must be canonical HTTPS without a trailing slash. `TRUSTED_PROXY_ADDRESSES` optionally lists exact IP addresses; absent means no trust in forwarded headers. Effective protocol must be HTTPS and raw Host must equal the configured authority. This intentionally leaves plain HTTP startup unusable for login; injection tests simulate an explicitly trusted loopback TLS proxy, without weakening Secure cookies. Operator commands do not require browser-origin configuration.

All authentication persistence operations share one fixed installation-local advisory transaction lock. Credential work runs outside that lock; login rechecks current credentials/status/grant and consumes CSRF state atomically before issuing a session. Staff mutations and recovery recheck their authority inside the mutation transaction. Counter reservations commit even on later login failure; rejected windows are never extended. A periodic unreferenced timer starts cleanup after 60 seconds, deletes at most 100 expired entries per state table/pass, and stops on module shutdown; no immediate connection is made during Nest composition. Security events have no automatic retention deletion until the deployment retention policy is settled.

The offline `0001_staff_access.sql` migration adds Authentication-owned session, pre-login, throttle and event tables only. It is not applied under source authorization. Shared-worker/restart guarantees depend on actual PostgreSQL acceptance, not serialized test doubles. Existing BA-01 migration/application evidence is preserved and does not establish BA-02 runtime behavior.

The forward offline `0002_login_reservations.sql` migration adds the bounded `pending_ids` UUID array to account throttle rows; source counters cannot retain pending IDs. Login success settles its own reservation atomically with session creation and preserves other in-flight attempts. Failure settlement is idempotent, including a repeated cleanup after an uncertain commit response; absent/expired/replaced reservations cannot modify a new window. No automatic migration or runtime acceptance is implied.

### Source contract and boundaries

- `AccessService.runAuthorized<T>(proof: Proof, policy: AuthorizedPolicy, work: AuthorizedOperation<T>): Promise<T>` is exported through Authentication `public.ts`, with `AuthorizedPolicy = staff | administrator` and `AuthorizedOperation<T> = (scope: AuthorizedScope) => Promise<T>`. Scope is `{ installation: InstallationContext, transaction: TransactionContext }`; unknown runtime policies fail closed. Authentication validates proof, current role/grant/status/password restrictions and session-bound CSRF, touches session activity in the same transaction, then invokes a bounded consumer callback with trusted business/branch configuration and the active opaque transaction context. It returns the callback's safe application result. No session secrets, account credentials, AccessUnit or query builders cross the boundary.
- Reuse existing access policy and lock. Order: access lock → authority/context/CSRF checks → consumer validation/writes → commit. A revocation committed first denies the callback; a callback admitted first may finish before the waiting revocation. Requests starting after revocation cannot regain authority.
- A private callback-failure marker traverses transaction rollback; afterward the original consumer error is rethrown unchanged so its owning HTTP boundary can map domain failures to standard Nest exceptions. Existing filtering sanitizes `BadRequestException` to 400/Invalid input, `ConflictException` to 409/Conflict, and arbitrary errors to 503/Service unavailable. Access failures retain existing status/message; other transaction/commit/rollback failures normalize to AccessError 503. If rollback replaces the callback error, the infrastructure failure takes precedence. Scoped rollback evidence is recorded in the delivery tracker; the callback must not catch-and-return a failure after performing writes.
- Callbacks perform bounded database work only: no network, hashing, nested transactions, re-entry into Authentication operations that acquire the lock, or additional connections. Authentication owns account/session access; the consumer owns its data. Business is accessed through its public interface. This does not authorize a generic permission framework or shared repository.
- The supported [http/public.ts](../../../http/public.ts) exports `AccessEntry`, `proof` and `AccessRequest`. Existing `AccessService` Nest provider export is unchanged; types are declared in [authorized-operation.ts](../../../application/authorized-operation.ts). Reuse the existing global guard/filter; no second guard stack, cookie parser, login route or permission designer. No production probe route or Menu implementation belongs to MN-00.
