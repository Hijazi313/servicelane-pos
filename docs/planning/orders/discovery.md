## Proposed first outcome

Plan one backend increment, **OR-01: record and read an order submitted at the counter**, with one or more configured Menu selling units and positive line quantities. Counter/takeaway capture and readback is approved as the first planning outcome; detailed contracts and acceptance remain proposed.

## Product decisions approved for planning — 2026-10-20

1. **Journey:** counter/takeaway capture and readback, without persisted carts, kitchen dispatch or payment.
2. **Price changes:** reject an attempted capture if merchandise prices have changed before submission and require reconfirmation of updated amounts. The expected-amount protocol below is a proposed technical mechanism, not an approved contract or proof of customer consent.
3. **Tax boundary:** this development increment records merchandise amounts only. Tax is unresolved, never zero/exempt by inference; there is no payable total, fiscal sale or receipt. No tax applicability, inclusive/exclusive treatment or accountant approval is asserted. Follow [compliance guidance](../../compliance/README.md) before activating affected operational workflows.

Captured means stored only, never paid, dispatched or fiscally finalized. Tax calculation, payment recording and sale-time fiscal snapshot ownership/timing remain to be decided during later discovery; they are not assigned by this proposal. Kitchen/payment ordering (including prepayment), amendments and cancellation must be resolved before operational use.

## Proposed OR-01 contract and boundaries

These details are recommendations for review, not additional approved requirements or available APIs.

- **Interface:** create one captured takeaway order and fetch one order by opaque ID. Include optional order-local customer name/phone and optional order-level/per-line instructions, as approved during review. No reusable customer directory, listing/search, draft-cart API, table or delivery-address fields. Request ownership is server-resolved; reject client-supplied business/branch, state, tax or payable totals.
- **Bounds:** retain the existing 16,384-byte request limit. In response to the user’s configurability request, propose business-scoped settings with defaults of 50 lines and 100 units per line; positive integer hard ceilings of 500 lines and 1,000 units per line remain technical safeguards, not industry defaults. Minimum order size/line quantity is one. A larger configured limit never overrides transport or response budgets. Menu retains its own selection limits. Both body size and semantic limits apply; 50 maximally complex lines need not fit. Reject unknown fields and malformed/overflowing amounts before persistence.
- **Expected amounts:** each line supplies its Menu selection, quantity and expected unit merchandise amount. Propose expected unit minor amounts as canonical unsigned base-10 integer strings, with currency/scale supplied once for the request. Menu returns the current unit minor amount and currency/scale; Orders compares these exact values. Decimal parsing and configured currency precision remain Menu-owned. The HTTP boundary validates integer-string syntax/length without deriving scale or reusing Menu’s configured-price ceiling. Compare every line, rather than only an aggregate where increases/decreases could cancel. On mismatch return only affected line indexes, current unit minor amounts and current currency/scale, rather than expanded composition, and conflict; no order or successful retry record is committed. A client reviews it and resubmits with updated expectations. Menu may change again, requiring another comparison. Existing single-selection HTTP preview remains nonbinding.
- **Menu application boundary:** propose one read-only batch resolution operation accepting trusted authorized installation/transaction scope and bounded selections. Read the catalogue once, reuse existing Menu selection rules, and return only selected identities/names/composition, currency/scale, canonical unit amounts and exact minor-unit integers. Expected-price comparison belongs to the Orders capture policy, not Menu pricing. No foreign persistence types, raw catalogue or query builders. Currency parsing/precision and configured unit pricing remain Menu-owned; Orders owns expected-amount comparison and integer quantity multiplication/summation. Propose a 24-digit nonnegative minor-amount ceiling for stored line/order amounts and expected unit strings, with bigint arithmetic internally and strings at JSON boundaries; reject overflow before writes. This is a representation bound, not a restaurant price rule. Application results/errors remain independent of HTTP; the Orders HTTP boundary maps them.
- **Transaction coordination:** creation invokes existing staff-policy `runAuthorized` once, then uses only the callback's trusted scope and active transaction. Menu reads its own data; Orders writes only its own order/lines/retry records. All work is awaited and bounded; no nested authorization/transaction, extra connection or external I/O. Shared authorization locking already serializes these current mutation paths; batch resolution must still use one catalogue snapshot. Do not assume a transaction alone prevents all future concurrent catalogue changes.
- **Read authorization:** use the existing shared HTTP staff policy and current installation resolution pattern, then query only the trusted business/branch and requested order ID. Return indistinguishable not-found for absent/foreign IDs; do not expose a globally fetched record before checking scope. No new RBAC or client-selected context.
- **Snapshot ownership:** Orders stores resolved names/identities/components, submitted selection, quantities and exact merchandise amounts at capture. It reads history from its own snapshot without re-resolving current Menu. Store currency/scale explicitly; no inference of fiscal meaning. One initial state, `captured`, with no state-transition API.
- **Retry semantics:** propose a 16–128 character opaque ASCII key scoped to business/branch, retained with the order with no expiry or cleanup API in OR-01. Compare a canonical validated request, including customer fields/instructions, selection, quantities and expected amounts, not raw JSON property ordering. Keep line order significant; normalize UUID case, optional empty selection arrays and unordered add-on/choice IDs through the supported Menu input contract without reading current catalogue state. Normalize before key lookup; malformed requests reject first. Apply immutable technical shape ceilings before replay, but evaluate current configurable business limits only for a new capture, after successful-key lookup; lowering a setting must not invalidate replay/readback of an existing order. Do not call current pricing merely to decide whether an existing success matches. Recheck current authorization first. An existing matching success returns its stored order before consulting current Menu, even after a price/availability change or process restart. Same key/different request conflicts. First successful capture and its key commit atomically; concurrent attempts yield one order. Enforce a database unique constraint on business/branch/key in addition to current serialized authorization; do not use an in-memory duplicate map. This is a future schema requirement, not migration authorization. Validation/price conflicts reserve no successful key; corrected resubmission may reuse it. Key possession grants no read access.
- **Errors:** propose 400 for invalid shape/bounds, existing 401/403 authorization behavior, 404 for absent/foreign offering or order identifiers, 409 for inactive/unsaleable selections, catalogue currency changes, expected-amount/currency mismatch or retry-content conflicts, and sanitized 503 for persistence failure. Preserve existing Menu error semantics where applicable; malformed selection remains 400, missing offering 404 and unavailable selection 409, matching the current resolver. Oversized input uses the existing transport 413. Distinguish Orders price-mismatch and key-conflict codes without serializing exception messages, SQL or internal catalogue data. No partial aggregate on any failure.

### Proposed customer/instruction handling

Orders owns optional name (120 Unicode code points), phone (32 characters, digits with optional leading plus and display separators), order instructions (500 code points) and line instructions (250 code points). These are proposed validation bounds, not approved business limits. Trim surrounding whitespace; normalize empty optional fields to absent for storage/retry comparison; reject invalid control characters and unknown fields. Preserve entered phone formatting after trimming, with no claim of verified identity, deliverability or international normalization. Instructions are plain text and do not change Menu composition/prices or guarantee kitchen execution. A later client must render them as text.

Include fields in the immutable captured snapshot, canonical retry comparison and authorized readback. Changed instructions/customer details with a successful key conflict; updates require a future amendment flow. Do not pass these fields to Menu or include them in generic logs/errors. Use synthetic identities only for future verification. No contact lookup, messaging, marketing consent, customer matching or personal data in retry keys. Retention, erasure, backup handling and downstream kitchen visibility remain unresolved policy for operational use; do not infer indefinite retention or permission to load real customer data. The order/key retention proposal is a development simplification, not a customer-data retention policy.

### Proposed configurable limit policy and evidence

Keep the policy in Orders-owned business-scoped settings, using trusted business identity, rather than adding Orders rules to Business installation context. Current Business capabilities provide validated installation/configuration, not a generic settings API. Propose a staff-readable effective policy and a narrow administrator-only complete update, with current revision and existing CSRF/transactional authorization. Persist only the two settings and revision; absent row uses documented defaults. No settings UI, generic settings framework, per-product overrides or branch overrides in OR-01. This is additional proposed phase P0 only if configurability is confirmed for OR-01; otherwise retain safe defaults and defer administration.

Validate settings against fixed ceilings; reject unknown fields/stale revision and never clamp values silently. New capture reads effective settings in the same authorized transaction. Successful replay/readback uses recorded history before evaluating current policy. Record the applied policy revision/effective limits with capture. Raising limits cannot raise the 16 KiB input or proposed 1 MiB response budget; capacity rejection remains explicit. Settings changes never rewrite orders.

Source evidence checked 2026-10-20: [Square open tickets](https://squareup.com/help/us/en/article/5337-use-open-tickets-with-square) documents a 500-item ticket limit, while [Square Online](https://squareup.com/help/us/en/article/7982-manage-square-online-item-settings-from-your-item-library) supports configurable per-order quantity limits. Tickets/items and online limits are not necessarily equivalent to our order lines/line quantities. These examples support bounded/configurable behavior, not a universal numeric standard; the reviewed sources do not establish an industry default for this counter workflow. Proposed 50/100 defaults are conservative product recommendations without restaurant workload evidence, not copied industry requirements.

## Technical review — 2026-10-20

- Source inspection: Menu catalogue reads use one SELECT; current Menu mutations and `runAuthorized` share AccessStore's installation-local advisory transaction lock. This supports coherent batch resolution under existing paths, not a general guarantee for future writers. Preserve the opaque transaction and public/provider export boundary.
- Money correction: configured single-price input allows only nine whole digits, whereas resolved prices sum base plus selected surcharges. Reusing that input ceiling for expected resolved amounts is unsound. The proposed integer-string contract avoids copying the precision registry or tightening valid resolved prices. The maximum 256 selected surcharges, proposed hard quantity ceiling 1,000 and 500-line ceiling fit the proposed 24-digit amount representation; this is a conservative source-derived bound, not an executed persistence result.
- Replay must precede live Menu resolution after current authorization and structural normalization. Otherwise a captured order becomes unrecoverable by retry after Menu deactivation or price changes. Current `me`/HTTP read pattern provides point-in-time authorization; no claim is made that a subsequent account revocation retroactively cancels an admitted read.
- Snapshot projection must copy only selected identities/names/components and amounts, not full Menu definitions or mutable references. Same-price name/composition changes are not detected by amount comparison. Confirming catalogue composition is outside the approved price-change decision; do not claim the proposal protects against every Menu edit.
- **Proposed response budget:** compact requests can expand substantially through combo components and names. Retain the 16 KiB input cap; propose a separate 1,048,576-byte UTF-8 JSON budget for the complete success/read representation, including customer/instruction fields, applied policy and maximum-width generated metadata, checked before capture commits. This bounds persisted expansion and response work; suitability for real counter orders still needs business review because no workload measurements exist. Reject excessive expansion atomically with a distinct 409 capacity code, never truncate components. The user must review that some complex orders within line/quantity limits may still be rejected; 50 maximally complex lines are not guaranteed. A stored order must remain readable within the same budget without consulting Menu. Acceptance checks include inclusive byte boundary, one byte over, multibyte/escaped names and rejection without retry-key reservation. Price-conflict output is limited to at most the hard ceiling of 500 line amount entries and omits expanded snapshots.
- Proposed focused checks must cover the response budget, resolved amounts above the configured single-price ceiling, canonical retry equivalence, same-price Menu edits, foreign IDs, no partial writes and current-authority replay. Existing Menu evidence is reused; no runtime checks or database actions were performed for this review.
